## Context

Le parcours visé (D84) : Guillaume copie un lien, la personne l'ouvre, installe drop, clique « Rejoindre », puis « Connecter mes agents ». Les briques existent : code d'invitation à jeton unique et ticket d'admission signé (T2.1), carte de confirmation avant appairage (T4.14), raccordement des agents (T3.3, T4.22). Il manquait le lien qui marche sans l'app, la signature de l'invitation, sa survie au redémarrage de l'inviteur, et le relais : un poste neuf démarre sur le relais de bouclage et n'atteint jamais celui de l'équipe.

Sources lues pour les choix techniques :

- Fragment d'URL : jamais envoyé dans la requête HTTP (RFC 9110, section 7.1 : la cible d'une requête est l'URI sans son fragment) ; jamais dans `Referer` (Fetch Standard, « strip url for use as a referrer » retire le fragment).
- CSP par empreinte d'un script en ligne (`'sha256-…'`, source « hash » de CSP Level 3) et `connect-src 'none'` qui interdit `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource` et `sendBeacon`.
- Liens profonds Tauri 2 (v2.tauri.app, « Deep Linking », lue le 11 octobre 2026, déjà citée par D84) : l'URL arrive par `on_open_url` ou `get_current`, parfois après le démarrage ; l'app la met déjà en file tant que le Node ne répond pas.

## Goals / Non-Goals

**Goals:** un lien unique, daté, à usage unique, signé ; une page statique qui ne transmet rien ; la même carte de confirmation qu'un lien `drop://pair` ; le bon relais sans réglage ; des refus explicites à codes stables ; aucune invitation dans un journal.

**Non-Goals:** noms des fichiers de release (aucune release encore) ; panneau React (autre chantier) ; déploiement VPS (T4.6a) ; preuve de l'identité humaine de l'inviteur (la carte invite toujours à vérifier avec la personne).

## Decisions

1. **Format du lien** : `https://drop.memolabs.dev/join#<code>`, où `<code>` est le code d'invitation existant (base64url du JSON). Rien d'autre dans l'URL. Une équipe auto-hébergée peut fixer `joinPage` dans `config.json` (https, sans requête ni fragment).
2. **Signature** : `sig` = Ed25519, par la clé d'identité de l'inviteur, du JSON canonique de tous les autres champs (`canonical`, `signDetached` existants : aucune crypto nouvelle). `verifyInvite` vérifie la signature contre `nodeId`, la date (au plus 24 h plus la tolérance d'horloge) et que le ticket d'admission est parrainé par ce même `nodeId`. Le nom affiché et le nom d'équipe refusent caractères de contrôle et marques bidirectionnelles (`isUnsafeLabel`). Une invitation non signée est refusée : il n'y a pas d'utilisateur extérieur à préserver, et une signature facultative ne protégerait rien.
3. **Usage unique des deux côtés** : l'inviteur supprime le jeton au premier `pair_request` (existant) et persiste ses jetons vivants dans `invites.json` (`0600`, écriture durable), pour honorer un lien après redémarrage ; l'invité garde l'empreinte SHA-256 des jetons acceptés jusqu'à leur expiration et refuse `E_INVITE_USED`. Le relais garde son refus de nonce déjà servi (T2.1).
4. **Relais adopté au clic, pas au premier lancement** : l'accord initial prévoyait que le premier lancement crée l'identité avec le relais de l'invitation. Retenu à la place : le relais change au moment de « Rejoindre », si le Node n'a encore ni pair ni équipe. Raisons : l'installeur Windows ou l'utilisateur lancent souvent drop avant de cliquer sur le bouton de la page, et le Node serait alors resté sur le bouclage ; un clic sur « Refuser » ne laisse ainsi aucune trace ; et le contrôle reste dans le Node, la coque Tauri ne lit jamais l'invitation. `config.json` est réécrit sous le verrou de migration, par fichier temporaire renommé et seulement s'il n'a pas changé ; `RelayClient.switchUrl` ferme la connexion et rejoint le nouveau relais avec le ticket d'admission. Un Node déjà relié garde son relais (`kept`) : l'appairage passe alors par tous ses chemins (relais, réseau local, iroh), comme avant.
5. **Politique de relais** (`relayUrlAllowed`) : `ws:` seulement vers une adresse privée ou de bouclage littérale (règle existante) ; `wss:` vers une telle adresse ou vers un nom DNS, jamais d'identifiants, de requête, de fragment, d'adresse publique littérale ni d'écriture non canonique. Puis, si une politique d'organisation est déployée, sa liste `relays`. Dans le profil privé, un relais DNS ne rejoint pas les destinations réseau du runner : seul le Node lui parle (D95).
6. **Page `/join`** : servie par `scripts/site.ts` à `/join`, `/join/`, `/join.html` et `/join/index.html` (pour un export statique), avec sa propre CSP : `default-src 'none'`, script épinglé par empreinte calculée à la construction, `connect-src 'none'`, `form-action 'none'`. La même politique, sans `frame-ancestors`, est aussi dans une balise `meta`. Le script lit le fragment, le garde dans `sessionStorage` de l'onglet et le retire de la barre d'adresse, écrit les noms par `textContent` seulement, détecte le système par `navigator.userAgent` et propose les trois téléchargements. Il n'a pas de crypto : la page n'est qu'un affichage, l'app vérifie tout avant d'envoyer quoi que ce soit.
7. **App** : `drop://join?invite=<code>` et `drop://pair?code=<code>` donnent le même paramètre `pair` au panneau local, donc la même carte T4.14. Le code doit être en base64url, le lien au plus 4 096 caractères. Mon espace (React) gagne « J'ai reçu une invitation » : code ou lien collé, aperçu, « Rejoindre » ou « Refuser ».
8. **API** : `POST /ui/invite` → `{ code, link, validHours }` ; `POST /ui/pair/preview` → `{ displayName, team?, relayHost, relay, expiresAt }` ; `POST /ui/pair` → `{ nodeId, relay, next: 'connect_agents' }`. Les deux dernières acceptent un formulaire (`code=`) ou du JSON (`{ code }`), code ou lien. Refus : 400 `{ error, code, message }`, message en français sans écho de l'invitation.

## Risks / Trade-offs

- [Le lien circule par messagerie et reste dans l'historique] → usage unique, 24 h, et ne donne qu'une admission au relais et une demande d'appairage que l'inviteur accepte d'office pour ce jeton ; chaque question reste soumise au consentement. La page retire le fragment de la barre d'adresse.
- [Nom affiché trompeur, « Guillaume » par un autre] → la signature lie le nom à la clé de l'émetteur, pas à la personne ; la carte demande de vérifier avec la personne avant de rejoindre (texte T4.14 conservé).
- [Relais malveillant dans une invitation forgée] → la signature empêche de changer le relais d'une vraie invitation ; une invitation forgée de bout en bout est celle d'un inconnu, que la carte montre comme telle ; le relais ne voit que des enveloppes chiffrées.
- [Hébergement statique du site par le dépôt d'infrastructure] → s'il impose `script-src 'none'` à toutes les pages, `/join` ne lit pas l'invitation : il doit servir la CSP de la page ou passer par `node scripts/site.ts serve`. À vérifier au déploiement (T4.6a).
- [Destinations du runner après adoption] → elles sont recalculées dans `config.json` mais ne s'appliquent aux capacités qu'au prochain démarrage du daemon ; l'ancienne origine était celle du relais de bouclage.
- [Windows et Linux : un lien `drop://` lance un nouveau processus] → la page Tauri « Deep Linking » le dit et recommande le plugin `single-instance` avec sa fonction `deep-link` ; la coque ne l'a pas encore. Sans lui, cliquer « Rejoindre l'équipe » avec drop déjà ouvert lance une seconde app au lieu d'ouvrir la carte. À ajouter par le chantier des builds Windows et Linux (T3.8, nouvelle ligne T4.31) ; sur Mac, le système remet le lien à l'app ouverte.
