La réponse traverse.
Le propriétaire décide.

Guillaume veut savoir si le dépôt de Julie gère le mode sombre. Son agent lui pose la question via une capacité publiée par Julie. Elle voit la demande, choisit de l'autoriser, puis relit la réponse avant qu'elle parte.

  1. Une question et une raison. L'agent choisit dans les capacités disponibles. L'entrée est validée avant l'envoi.
  2. Un accord pour cette demande. Le propriétaire peut autoriser une fois, refuser ou répondre plus tard.
  3. Une exécution encadrée. Les outils, le budget et la forme de la réponse sont fixés par la capacité.
  4. Une relecture quand c'est sensible. Les réponses sur le code ou sur un serveur MCP repassent par le propriétaire.
  5. Une réponse et une trace. Le demandeur reçoit le résultat autorisé. Le reçu signé conserve des empreintes et des métadonnées.

Et si la réponse est non ? Un refus termine cette demande. « Pas maintenant » ne déclenche aucune relance automatique. Une demande expirée n'est pas exécutée.

Chacun garde son environnement.

Un Node est le processus drop qui tourne sur une machine. Il porte son identité et ses demandes. Le relais permet à deux Nodes de se joindre à distance. Le runner exécute une action chez le propriétaire.

Une capacité, c'est un contrat d'action.

Elle décrit ce que l'on peut demander, les outils utilisables, le résultat attendu, sa sensibilité et son budget. Une question reçue ne peut pas élargir la liste des outils.

Capacité Ce qui revient
production.error_summary État du service, compteurs et catégories d'erreurs. Sans modèle.
repo.answer Réponse courte, verdict et noms de fichiers. Avec relecture.
mcp.answer.<nom> Réponse courte et noms de sources d'un outil connecté. Avec relecture.

L'agent a trois outils.

list_capabilities   Découvrir les capacités
request_drop        Envoyer une demande
get_drop_result     Récupérer la réponse

MCP est le format de connexion entre l'agent et ces outils. Le connecteur parle à l'API locale du Node ; c'est le Node qui rejoint le relais.

Qui reçoit quoi ?

La promesse porte sur le partage d'une réponse autorisée. Pour l'évaluer, il faut aussi regarder le chemin du contexte utilisé pour fabriquer cette réponse.

Destinataire Informations reçues
Le demandeur La sortie bornée et autorisée, sans accès permanent aux sources.
Le relais Du contenu chiffré et les métadonnées nécessaires au routage.
Le propriétaire La question et sa raison ; il utilise ses propres accès.
Un fournisseur LLM distant La question et les résultats d'outils transmis au modèle.

Localité et confidentialité sont deux sujets distincts. Le fournisseur configuré par défaut est OpenRouter. Si un modèle distant est utilisé, du contexte peut lui être transmis. Un modèle local compatible peut être configuré.

Le contrôle des outils, la validation du résultat, le scanner de secrets et la relecture forment plusieurs protections. Ils ne constituent pas un audit indépendant ou une garantie absolue contre une fuite. Les outils MCP partagés doivent être examinés par le propriétaire.

Essayer, côté développeur.

Le prototype se lance depuis le dépôt. L’installation locale des connecteurs existe. Le paquet npm public et l’app Mac restent à distribuer.

1. Vérifier les prérequis

Un clone du dépôt, Node 22.18 ou supérieur et pnpm 11.27.0, version déclarée lors de ce bilan. 

pnpm install
pnpm -r lint
pnpm -r typecheck
pnpm -r test

Les tests utilisent des données locales et des fournisseurs simulés. Aucune clé de modèle n'est nécessaire.

2. Rejouer la démo

bash scripts/demo-local.sh

Le script démarre un relais et trois Nodes temporaires sur les ports 7790 à 7793. Il joue un résumé d'erreurs puis une question sur un dépôt.

La deuxième partie utilise OpenRouter. Elle demande le réseau et une clé dans OPENROUTER_API_KEY, ou dans l'entrée macOS OpenRouter API Key. La durée dépend du fournisseur. Le script arrête ses processus à la fin et conserve le dossier temporaire.

3. Connecter son agent

Le Node doit être initialisé, autorisé sur un relais et lancé avec serve. Le guide téléchargeable détaille ces étapes et renvoie aux configurations Claude Code et Codex du dépôt.

Quelques questions utiles.

Qui paie le modèle ?

Le demandeur peut financer une demande avec une clé plafonnée et chiffrée pour l'exécuteur, si le financement est configuré. Le propriétaire peut aussi utiliser sa propre clé. Le payeur et le coût annoncé sont indiqués avant l'accord.

Est-ce que drop fonctionne avec Figma ou Notion ?

La capacité générique mcp.answer peut utiliser un serveur MCP déjà configuré chez le propriétaire. La liste d'outils est fixée à la publication. Les usages réels chez Julie et Natha restent une étape de validation, pas une intégration certifiée pour chaque outil.

Est-ce que toute l'équipe est découverte automatiquement ?

Un annuaire signé est maintenant implémenté. Rejoindre l’équipe par invitation propage les membres et leur appairage ; la commande team montre leurs agents et leurs capacités. L’app Mac et les demandes multiples restent à construire.

Est-ce un produit prêt à déployer en entreprise ?

Le cœur a été implémenté et démontré. Il reste notamment l’app Mac, la distribution publique, les essais utilisateurs et une dette de traçabilité entre specs et tests. Le bilan donne les preuves et les limites précises.
