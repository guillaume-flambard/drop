# Recherche technique : app desktop et modèles locaux

> Statut : recherche datée. Le cap privé et open source a été adopté le 9 octobre 2026 (D34 à D38). Les prix restent des hypothèses et les modèles des candidats non mesurés. Les décisions et chantiers actuels sont dans `docs/DECISIONS.md` et `docs/TASKS.md`.

Date de consultation : 9 octobre 2026. Sources officielles des frameworks et éditeurs, plus les mesures locales consignées dans D19. Recommandations pour le pivot souverain de drop ; ce document ne modifie pas les contrats ni ne valide un runtime.

## Recommandation 1 : garder Tauri 2 pour le shell desktop

**Décision recommandée :** conserver le shell Tauri 2 et le Node existants pour l’app Mac de barre de menus. Cela évite une réécriture sans avantage établi pour le besoin immédiat et garde une voie Windows/Linux. Le front web est rendu dans le WebView système : WKWebView sur macOS, WebView2 sur Windows, WebKitGTK sur Linux. Tauri utilise donc les composants natifs installés par l’OS, contrairement à Electron qui distribue Chromium et Node.js avec l’application. C’est une différence d’architecture, pas une mesure de mémoire, taille ou vitesse pour drop. [Architecture Tauri](https://v2.tauri.app/concept/architecture/), [versions de WebView](https://v2.tauri.app/reference/webview-versions/), [architecture Electron](https://www.electronjs.org/docs/latest/tutorial/process-model), [sécurité et composants distribués par Electron](https://www.electronjs.org/docs/latest/tutorial/security/)

Le dépôt configure déjà Tauri 2, `tray-icon`, une app sans fenêtre initiale et un binaire Node embarqué comme ressource : [Cargo.toml de l’app Mac](../../apps/desktop/src-tauri/Cargo.toml), [configuration Tauri](../../apps/desktop/src-tauri/tauri.conf.json). Ces ressources montrent un choix existant cohérent avec le besoin, pas la preuve que le cycle de vie du Node est déjà robuste.

| Option                  | Atouts pour drop                                                                                                                            | Coûts et limites documentés                                                                                                                                                                                                                                                                                                                                                         |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Tauri 2, recommandé** | Tray multiplateforme via Rust ; UI web existante ; peut embarquer et lancer un binaire sidecar pour éviter de demander Node à l’utilisateur | Les WebView diffèrent selon l’OS et sa version. Le sidecar doit être produit par cible et son lancement, arrêt, logs et redémarrage gérés par l’application. Linux demande les dépendances WebKitGTK et, selon le backend tray, AppIndicator ou StatusNotifierItem. |
| **Electron**            | `Tray` officiellement sur macOS, Windows et Linux ; main process Node.js offre une intégration directe avec le runtime JavaScript           | L’application distribuée inclut Chromium et Node.js ; cela ajoute une autre architecture et des mises à jour de sécurité à suivre. L’auto-updater intégré est Mac/Windows seulement ; sous Linux, mise à jour par gestionnaire de paquets. macOS exige une app signée pour l’auto-update. Aucun besoin produit identifié ici ne justifie le changement.                             |

Migrer obligerait à refaire le shell et le pont vers le Node et les composants web, puis à bâtir une autre stratégie pour les autres OS. Sources : [Tauri sidecar](https://v2.tauri.app/develop/sidecar/), [Tauri updater et signatures d’update](https://v2.tauri.app/plugin/updater/), [distribution Tauri et signature/notarisation](https://v2.tauri.app/distribute/), [prérequis Tauri par OS](https://v2.tauri.app/start/prerequisites/), [backend et limites Linux de tray-icon](https://github.com/tauri-apps/tray-icon), [autoUpdater Electron](https://www.electronjs.org/docs/latest/api/auto-updater/), [tray Electron](https://www.electronjs.org/docs/latest/api/tray/), [MenuBarExtra SwiftUI](https://developer.apple.com/documentation/swiftui/menubarextra).

**Risque pratique principal :** le tray Linux existe mais n’est pas uniforme. Le backend Tauri/tray-icon peut utiliser AppIndicator ou KSNI; les dépendances système et certains événements varient selon ce choix et l’environnement. Les issues officielles du dépôt montrent des cas Linux/Wayland à résoudre, donc traiter Linux comme support à vérifier par desktop et package, pas comme conséquence automatique de « multiplateforme ». [Tray-icon](https://github.com/tauri-apps/tray-icon), [issues Tauri tray Linux](https://github.com/tauri-apps/tauri/issues?q=is%3Aissue+tray+linux+wayland).

**Critères de vérification réutilisables :**

- Sur macOS, démarrage, fermeture, relance, veille/reprise, ouverture UI depuis le tray et fermeture complète de l’app ne laissent aucun Node orphelin ; les erreurs de démarrage et la sortie du Node sont diagnostiquables sans journaliser de secrets.
- Le Node embarqué et le shell sont signés dans l’artefact distribué. Tester installation et mise à jour macOS signées/notarisées, conservation des données locales, rollback ou interruption de mise à jour, et démarrage hors ligne.
- Sur Windows vérifier présence/runtime WebView2, lancement et arrêt du sidecar, signature installateur et mise à jour ; sur Linux tester au moins GNOME et KDE, Wayland et X11, avec tray et navigation sans tray. Énoncer exactement les distributions supportées.

## Recommandation 2 : choix local opt-in, avec Qwen3.5 comme candidat à mesurer

Ne promettre aucun modèle local comme « fonctionne pour tout le monde ». Le choix gratuit au coût marginal zéro doit être l’agent ou le modèle déjà fourni et contrôlé par le propriétaire, notamment via un serveur A2A existant. Pour un mode autonome, proposer le provider OpenAI-compatible local (Ollama est déjà compatible avec D19), et ne télécharger un modèle qu’après affichage du nom, de la licence, de la taille, de l’espace requis et confirmation explicite. Ollama offre des modèles locaux et cloud : n’utiliser ici que les identifiants sans suffixe `:cloud` et le endpoint localhost. Aucun quota gratuit hébergé ne constitue une garantie de service. [API Ollama avec outils](https://docs.ollama.com/capabilities/tool-calling), [Ollama Qwen3.5](https://ollama.com/library/qwen3.5)

Toujours mesurer latence, usage mémoire et exactitude avant de le sélectionner comme défaut. |

**Mesures réelles existantes, à ne pas extrapoler :** D19 dans [docs/DECISIONS.md](../DECISIONS.md) rapporte que `qwen3:0.6b`, déjà installé, n’a appelé aucun outil et a répondu « unknown ». `qwen3:8b` a pris 60 à 166 s, appelé parfois les outils et cité un faux fichier. Le modèle 120B gratuit OpenRouter était exact dans deux questions, mais il est distant, soumis au quota et incompatible avec une garantie souveraine. Aucune mesure française ou sur Qwen3.5 4B/9B n’est consignée. Le support du tool calling par le format ou le serveur ne prouve pas que le modèle choisira les bons outils, arguments ou réponses.

**Critères d’acceptation du modèle local :**

- Réutiliser le modèle local déjà installé ou un endpoint A2A propriétaire si l’utilisateur les choisit ; aucun téléchargement, pull ou appel cloud silencieux.
- Avant un pull, indiquer nom/version, licence, taille disque connue, mémoire non garantie, destination de stockage et que le coût de calcul/énergie est porté par l’appareil. L’utilisateur peut refuser et continuer avec un modèle configuré ou une capacité déterministe.
- Valider chaque candidat sur questions bornées en français : outil appelé, nom d’outil autorisé, arguments conformes, refus/inconnu lorsque les sources ne suffisent pas, exactitude de la réponse, latence et pic mémoire sur plusieurs Mac de mémoire différente. Le runner garde la liste d’outils fixée par capacité, indépendamment du modèle.
- Bloquer Internet après installation et observer les connexions pendant une requête locale ; le modèle doit répondre avec les données locales sans service cloud. La seule présence des poids sur disque n’est pas cette preuve.
- Classer par mémoire disponible mesurée et espace disque, avec seuils dérivés de tests réels par version et contexte. Ne pas coder des seuils de RAM à partir des seuls nombres de paramètres ou tailles de fichiers publiées.

## Sources d’incertitude

Les pages éditeur établissent les architectures, formats, plateformes et licences ci-dessus, non la qualité en français, les performances, l’usage RAM précis ou le comportement du sidecar de drop. Aucune mesure comparative Tauri/Electron/SwiftUI n’a été faite, et aucune inférence de vitesse ou d’autonomie ne doit être tirée du seul choix du framework. Aucun modèle n’a été téléchargé ou testé dans cette recherche.
